# 상세페이지 카피 사전 검수기 (copy_lint) v1.2

렌더 단계 **앞과 뒤**에서 돌려서, 고객에게 나가면 안 되는 문장과 산출물을 잡는 린터입니다.
표준 라이브러리만 쓰므로 설치할 게 없습니다 (Python 3.8+).

```
qa/
├── copy_lint.py     검수 엔진 + CLI
├── rules.json       검수 규칙 (v1.2.0)
├── test_lint.py     회귀 테스트 41항목
└── sample/
    ├── rendered_regulatory_mat.json  1차 산출물(결함 포함) - FAIL 픽스처
    ├── copy_regulatory_v2.md         2차 산출물 카피 소스
    ├── rendered_text_v2.txt          2차 산출물의 렌더 문장 덤프(육안 확인분)
    ├── clean_example.json            교정 카피 - PASS 픽스처
    └── report*.json                  리포트 JSON 예시
```

## 1. v1.0 → v1.1 변경점

| # | 변경 | 이유 |
|---|---|---|
| 1 | **`--rendered-text` 모드 추가 (L026/L027)** — 렌더된 문장과 카피 소스를 대조 | 2차 산출물에서 카피.md는 "샤워", 렌더 이미지는 "사워"였다. 소스만 검사하면 못 잡는다 |
| 2 | **L006 오탐 완화** — 구성 분리 서술(겉커버/속매트 등)이 있으면 P1 | "규조토 100% + 패브릭"이 실제로는 겉커버/속매트 구조라 정당한 표기였다 |
| 3 | **L012 오탐 완화** — 화면에 보이는 라벨만 P0, 섹션/파일명만이면 P2 | 이미지에는 "생활 발매트"로 나오는데 파일명만 "후기카드"여서 오탐 |
| 4 | **L025 신규** — 부정 비교 주장(석고 등) | "석고 0%"는 경쟁 제품 소재를 깎는 주장인데 근거가 없었다 |
| 5 | `planning_phrases` 확장 — "원본에", "원문에", "템플릿" | "원본에 고객센터 표기가 있어요"는 고객에게 의미 없는 제작 메모 |
| 6 | 같은 문장이 소스와 렌더에서 모두 잡히면 소스만 보고 | 중복 지적으로 리포트가 길어짐 |

### v1.1 → v1.2 변경점

| # | 변경 | 이유 |
|---|---|---|
| 1 | **`customer_core` 추가** — who/pain/solution/gain/objection | 페이지 전체가 고객의 불편→해결→이득을 한 번씩만 말하게 한다 |
| 2 | **섹션 계약(`customer` + `contract`) 추가** — buyer_question/focus/one_sentence_answer/proof_type/proof_ref/new_information/forbidden | S1~S9가 같은 주장을 반복하지 않고, 섹션마다 다른 구매 질문 하나를 맡게 한다 |
| 3 | **L028~L034 신규** — 계약 누락/답 반복/증거 유형 다양성/근거 재사용/고객 코어/고객 메모/새 정보 | 말투가 아니라 구조를 검사한다. `_contract_required: true`인 파이프라인 입력에만 강제한다 |
| 4 | `product_inferred` 객체 처리 | `{product_name: ...}`가 들어와도 `check_name_repeat`가 죽지 않게 한다 |

`customer`는 카피를 쓰기 전에 참고하는 메모입니다. 실제 화면에는 `contract.focus`에 해당하는 내용만 드러내고, S2(불편)·S4(해결)·S3/S7(이득)이 페이지 전체에서 한 번씩만 등장하게 합니다.

## 2. 실행

```bash
# 카피만
python qa/copy_lint.py --copy copy.json

# 이미지까지
python qa/copy_lint.py --copy copy.json --images-dir ./output

# 렌더 결과 문장까지 대조 (권장)
python qa/copy_lint.py --copy copy.json --images-dir ./output \
    --rendered-text rendered.txt --json-out report.json

# P0가 있으면 종료코드 1
python qa/copy_lint.py --copy copy.json --strict

# 회귀 테스트
python qa/test_lint.py
```

`rendered.txt` 형식: **한 줄에 노출 문장 하나**. `#`으로 시작하는 줄은 주석으로 무시합니다.

```
빨아 쓰는 2세대 규조토 발매트
아이 목욕 뒤
사워 뒤 나오는 첫자리에 둬요
```

종료 코드: `0` P0 없음 · `1` P0 발견 · `2` 입력 오류

## 3. 입력

JSON(권장) 또는 카피.md 둘 다 됩니다.

```jsonc
{
  "product_name": "무압박 수면양말 4종세트",
  "review_count": 0,
  "sections": [
    {"id": "S1", "name": "히어로", "label": "무압박 수면양말",
     "headline": ["줄1", "줄2"],
     "description": "섹션 서브카피",
     "points": [{"key": "밴드", "text": "고객에게 보이는 설명문"}],
     "tiles": ["4켤레", "45g"]}
  ]
}
```

- `points[].key`는 검사 제외(짧은 명사가 오탐을 만든다). `text`만 본다.
- `review_count`가 0일 때만 L012가 켜진다.

앱 파이프라인은 여기에 고객 인사이트와 섹션 계약을 더해 보냅니다.

```jsonc
{
  "_contract_required": true,
  "customer_core": {
    "who": "겨울밤 발이 찬 30대 직장인",
    "pain": "양말 밴드가 조여서 자국과 저림이 생긴다",
    "solution": "넓은 파일 밴드가 압력을 여러 줄로 나눠 받는다",
    "gain": "아침까지 발목이 편안하고 숙면을 방해하지 않는다",
    "objection": "가격과 세탁 편의성"
  },
  "sections": [{
    "id": "S2",
    "name": "문제 공감",
    "headline": ["양말 자국이 남는 밤"],
    "customer": {"pain": "밴드가 조여 자국이 남는다", "solution": "압력을 나눠 받는 편직", "gain": "자국 없이 편안한 밤"},
    "contract": {
      "buyer_question": "내 불편을 알기는 하나?",
      "focus": "pain",
      "one_sentence_answer": "밤마다 양말 자국과 저림이 남는다",
      "proof_type": "pain_scene",
      "proof_ref": "원본 S2",
      "new_information": "밴드가 조이는 불편 장면",
      "forbidden": ["제품 기능", "해결책"]
    }
  }]
}
```

`_contract_required`가 없고 계약 필드도 전혀 없는 예전 입력은 L028~L034를 건너뜁니다(하위 호환).

## 4. 파이프라인 연동

```python
from qa.copy_lint import lint, print_report, RenderBlocked

report = lint(payload, images_dir=out_dir, rules_path="qa/rules.json",
              rendered_text=rendered_dump)
if report["blocked"]:
    print_report(report)
    raise RenderBlocked(report)

render(payload)
```

- **P0 = 차단** (법적·신뢰 리스크)
- **P1 = 경고** (전환 손실, 승인 시 강행 가능)
- **P2 = 참고** (중복·용량·구성)

리포트: `blocked`, `verdict(FAIL/WARN/PASS)`, `counts`, `rendered{lines,matched,coverage}`, `issues[]`

## 6. 실제 검수 결과 (v1.1로 측정한 과거 결과)

| 대상 | 구성 | P0 | P1 | P2 | 판정 |
|---|---|---|---|---|---|
| 규조토 1차 (01:54) | 8섹션 18.33MB | 20 | 16 | 0 | FAIL |
| 규조토 2차 (08:48) 카피만 | 8섹션 19.38MB | 5 | 13 | 4 | FAIL |
| 규조토 2차 + 렌더 텍스트 | 위와 동일 | 5 | 13 | 4 | FAIL |
| 교정 카피(clean_example) | 4섹션 | 0 | 0 | 0 | PASS |

2차에서 P0가 20 → 5로 줄었고, 남은 5건은 모두 실제 문제입니다.

1. `원본에 100% 규조토 표기` — 제작 메모 (L001)
2. `원본에 고객센터 표기가 있어요` — 제작 메모 (L001)
3. `사워 뒤 나오는 첫자리에 둬요` — 렌더에서만 발생한 오타 (L003, **렌더 대조로만 잡힘**)
4. 상품정보 고시 섹션 없음 (L008)
5. `비교표에 석고 0%로 표기` — 근거 없는 부정 비교 (L025)

## 7. 규칙 늘리는 법

`rules.json`만 고칩니다. 코드 수정 없음.

```jsonc
{
  "typos": { "몇일": "며칠" },
  "planning_phrases": ["보여주는 컷"],
  "claims": ["정전기 방지", "냄새 없"],
  "negative_comparatives": ["라텍스"],
  "composition_markers": ["상판", "하판"],
  "evidence_markers": ["시험성적서 번호"]
}
```

사전은 **부분일치**입니다. 2글자 미만 단어는 오탐을 만드니 넣지 마세요.

## 9. 한계

1. 사전 매칭이라 **처음 보는 표현의 효과 주장은 못 잡습니다.**
2. 맞춤법 전체 검사가 아닙니다.
3. 이미지 내용은 보지 않습니다(용량·중복·비율만).
4. `--rendered-text`는 **텍스트 덤프를 넣어야만** 동작합니다. 렌더러가 그린 문자열을 덤프하도록 파이프라인을 고쳐야 진짜 효과가 납니다(핸드오프 문서 6장).
5. P0 0건이 "좋은 상세"를 뜻하지 않습니다. 설득력(훅·전후 비교·체크리스트)은 별도 스펙의 영역입니다.
6. 섹션 계약 검사(L028~L034)는 필드 존재와 문장 유사도만 봅니다. 고객의 불편이 실제로 설득력 있는지, 해결이 제품 사실과 맞는지는 이미지·카피 검수자가 최종 확인해야 합니다.
